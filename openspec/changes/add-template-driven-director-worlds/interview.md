# Interview Notes: Agentopia Director-Style Cultivation World

## 项目一句话

这个项目是一个长期多智能体生活模拟系统：它让一群拥有个人设定、记忆、关系和目标的角色在同一个世界里持续生活、交流、行动和变化。现在的新方向是把它改造成一个“导演型养成世界”后端，让玩家不直接改角色数值，而是通过投放事件、加入角色、观察世界演化来创造故事。

## 我做了什么

### 已有项目能力

- 搭建了一个可以长期推进的多智能体世界循环，包括周计划、社交接触、活动、回顾、结算、年度更新等阶段。
- 为每个角色维护独立的 profile、state、memory、scratchpad、contact、schedule 和生成记录，让角色不是一次性对话，而是有持续状态和关系记忆。
- 实现了角色之间的互动流程，包括主动联系、共同活动、独处活动、公共事件感知、礼物、关系判断和阶段总结。
- 加入了世界层的 God Model，用来生成公共事件、评估状态变化、设计职位、更新人物画像、产生遭遇机会。
- 加入了奖励和经济相关机制，例如社交 PageRank、主观奖励、经济奖励、优势估计等，使模拟结果可以用于后续分析或训练。
- 使用文件系统和 JSONL 作为运行记录，让每一轮模拟都有可追踪的中间产物。

### 这次准备改进的方向

- 从“研究型模拟 runner”升级为“可创作的导演型世界引擎”。
- 引入 world template，让校园班级、合租公寓、偶像事务所、幻想学院等场景都可以按模板创建，而不是写死在代码里。
- 先做一个 `school-classroom` 模板，定义班级节奏、角色类型、地点、事件类型、入场方式和可视化提示。
- 引入 director event，让玩家通过结构化事件影响世界，例如传闻、压力、机会、偶遇、校园事件、转学生到来。
- 支持运行中加入角色，例如转学生、新老师、社团访客，但角色状态要通过模板和模拟流程初始化，不能由玩家直接改数值。
- 输出 visualization snapshot，让 Godot 或其他客户端以后可以直接读时间线、角色卡、关系图、地点活动和事件结果。

## 核心架构讲法

可以把系统分成四层：

```text
┌──────────────────────────────────────────────┐
│ Director Layer                               │
│ 玩家投放事件、加入角色、选择推进时间          │
└───────────────────────┬──────────────────────┘
                        │
┌───────────────────────▼──────────────────────┐
│ Template Layer                               │
│ 场景模板：校园班级/公寓/未来自定义世界         │
│ 定义角色字段、地点、事件类型、加入方式        │
└───────────────────────┬──────────────────────┘
                        │
┌───────────────────────▼──────────────────────┐
│ Simulation Core                              │
│ World + RoleAgent + God Model                │
│ 负责计划、接触、活动、回顾、结算、关系变化    │
└───────────────────────┬──────────────────────┘
                        │
┌───────────────────────▼──────────────────────┐
│ Read Model / Visualization State             │
│ 给 Godot 读取的时间线、角色摘要、关系、地点   │
└──────────────────────────────────────────────┘
```

最重要的设计原则是：玩家不是数据库管理员，玩家是导演。玩家可以制造情境，但不能直接把“某个角色好感度 +20”或者“活力改成 10”。角色变化应该来自事件进入世界后，被角色的性格、记忆、关系和当前状态共同解释出来。

## 亮点

### 1. 长期状态，不是一次性聊天

很多 LLM 角色项目只解决“当前这句话怎么回”。这个项目更关注长期生活：角色每周计划、每天活动、社交、复盘，所有过程都会留下记录。这样角色关系和行为不是纯 prompt 幻觉，而是被持续状态和历史记录约束。

### 2. 多智能体关系网络

角色不是孤立的。系统会记录接触、共同活动、评价、社交影响和关系变化。后续可以把它可视化成班级关系图、阵营变化、冲突线和友情线。

### 3. 导演型玩法更适合降低成本

完全自由聊天会消耗大量 token，而且很难控制。导演型设计把玩家输入收束为结构化事件：事件类型、目标、地点、强度、持续时间、可见范围。这能减少无效生成，也让系统知道什么时候需要调用 LLM，什么时候可以用规则和缓存处理。

### 4. 模板化带来 extensibility

模板把“这个世界需要什么字段”抽出来。校园班级可以有年级、班主任、社团、考试压力；公寓可以有房租、邻里关系、公共空间；偶像事务所可以有粉丝、训练、舞台。核心模拟不用为每个场景重写一套。

### 5. 为 Godot 做后端准备

Godot 不应该直接读内部 JSONL、prompt、scratchpad。后端应该提供稳定的 visualization snapshot，让 Godot 只关心怎么渲染：时间线、角色卡、关系边、地点上的事件。这会让游戏客户端和模拟核心解耦。

## 难点

### 1. 自由度和可控性的平衡

如果玩家能输入任何自然语言命令，自由度高但系统很难验证，也很容易变成直接改状态。现在的方案是保留自由描述，但必须挂在结构化 director event 上。这样既能表达故事，又能让系统知道它是什么类型的干预。

### 2. 运行中加入角色很复杂

现在的 `World` 初始化时会一次性加载所有角色，并维护 `self.agents` 和 `_name2agent`。如果中途加角色，不只是新增 profile，还要初始化 state、memory、scratchpad、schedule、location、position，并在安全边界刷新 agent 列表。第一版最好限制在“周与周之间”加入，避免活动进行到一半时破坏调度。

### 3. 可视化不能绑死内部实现

内部数据是为了模拟和调试服务的，未来可能变化。Godot 需要的是稳定的读模型，所以 visualization snapshot 必须是派生数据，而不是新的事实来源。否则后端和客户端会互相拖住。

### 4. 成本控制不是单点优化

降低 GPU/token 消耗不是只换模型就能解决。更关键的是减少不必要的生成：模板提供默认结构，事件提供明确上下文，快照避免客户端反复解析原始记录，部分逻辑用规则处理，只在角色决策和高价值叙事节点调用 LLM。

### 5. 模板设计过宽会拖慢落地

如果一开始试图支持所有世界，模板会变得很抽象很重。所以第一版应该只把 `school-classroom` 做扎实，但字段设计保持通用：角色类型、地点、事件、加入方式、可视化 hints。这是一个从具体中抽象的过程。

## 技术取舍

- 使用 JSON template 而不是 YAML：项目当前不依赖 YAML parser，JSON 对 Python 和未来客户端都更直接。以后可以做 YAML 或表单编辑器，再导出 JSON。
- 先做后端，不做 web：当前核心风险在模拟流程和数据契约，不在界面。先把 Godot 未来要消费的数据形状稳定下来。
- 加角色先限制在周边界：牺牲一点即时戏剧性，换来调度、奖励、活动、关系计算的稳定。
- 事件不直接改状态：牺牲“玩家立刻看到数值变化”的爽感，换来角色自主性和故事可信度。
- visualization snapshot 作为读模型：多一层转换，但换来客户端稳定和后端可维护性。

## 可以怎么向别人解释

### 简短版

我做的是一个多智能体长期生活模拟项目。每个角色都有自己的设定、状态、记忆和社交关系，世界会按周推进，角色会计划、互动、活动、复盘并产生变化。现在我在把它升级成导演型养成世界：玩家不是直接控制角色，而是投放事件、加入角色，然后观察这个班级或世界如何演化。后续可以用 Godot 做可视化，把时间线、角色关系和地点事件展示出来。

### 技术版

核心是一个分阶段的 simulation loop。`World` 负责推进时间和调度阶段，`RoleAgent` 负责角色决策，`DataManager` 负责文件化状态和记忆，`God Model` 负责世界事件和状态评估。新方案会加入 template layer 和 director event layer：模板定义场景结构，导演事件定义玩家能投放的结构化干预。最终输出 visualization snapshot，作为 Godot 客户端读取的稳定数据接口。

### 产品版

这个项目想做的不是普通聊天角色，而是一个会自己发展的养成世界。玩家像导演一样往世界里放入角色和事件，然后看角色根据自己的性格、关系和记忆做出反应。第一版场景是校园班级，因为班级天然有固定地点、人物关系、事件节奏和戏剧冲突，适合验证系统。

## 可能被问到的问题

### 为什么不让玩家直接调角色状态？

因为直接调状态会破坏角色自主性，也会让故事变成数值编辑器。这个项目的核心乐趣是“我制造一个情境，然后角色自己反应”。所以玩家可以投放事件，但状态变化要通过模拟产生。

### 为什么先做校园班级？

校园班级结构清晰：学生、老师、教室、社团、考试、传闻、转学生、同桌关系。这些都很适合验证模板、事件、关系网络和可视化。它比开放世界小，但足够有戏剧性。

### 为什么以后接 Godot，而不是继续做 web？

这个项目的体验更接近游戏：地图、角色、时间线、关系网、事件反馈。Godot 更适合做这样的互动可视化，而 web 原型容易变成表单和仪表盘，不能很好表达“世界正在活着”。

### 怎么降低 token/GPU 消耗？

通过结构化流程减少无效生成：模板提供固定世界结构，director event 限制输入形状，角色只在关键决策点生成，公共事件和可视化快照可以缓存或规则化。也可以后续把不同任务分给不同模型，例如小模型做分类和格式化，大模型做高价值角色决策。

### 最大技术风险是什么？

动态角色加入和长期一致性。中途加入角色会影响调度、关系、记忆、地点和奖励，所以第一版必须在安全边界处理，并且把初始化流程做完整。另一个风险是模板过度抽象，所以第一版要围绕校园班级落地。

## 后续方向

- 先完成模板驱动的校园班级后端。
- 做 director event 和 character entry，让玩家能投放事件和加入角色。
- 生成 visualization snapshot，为 Godot 做稳定数据接口。
- 再做一个很薄的 Godot 原型，只负责显示班级地图、角色状态、关系线和事件时间线。
- 最后再考虑更多模板、玩家自定义编辑器、成本优化和更复杂的叙事系统。
